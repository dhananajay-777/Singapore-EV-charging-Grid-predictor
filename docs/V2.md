# V2: more data, same question

**Status:** in progress. Dhananajay's own continuation, separate from the
team submission (final report submitted 16 Oct 2026).

V1 was built on the first 14 days of collection. The logger kept running
after that, so V2 has roughly twice the data and rebuilds the dataset on the
full period. Collection has ended; V2 uses only what is already in `data/`.

## What changes

| | V1 (team submission) | V2 |
|---|---|---|
| Period | 11–24 Sep 2026 | 11 Sep – 14 Oct 2026 |
| Days | 14 | 34 |
| Samples | 85 | 173 |
| Weekends covered | 2 | 5 |
| Carparks in the feed | 1,995 | 2,007 |
| EV connectors | 11,429 | up to 11,698 (new chargers added during the period) |
| Connector status rows | about 970,000 | 1.99 million |

The extra weeks matter most for three things:

- **The faulty-charger rule** uses a 14-day window. With 34 days it can be
  checked over two separate windows, so a charger flagged in one and fine in
  the other was probably repaired, not broken.
- **Weekday and weekend profiles** move from two weekends to five.
- **Charger growth.** About 270 connectors and 44 stations appeared during
  the period. V2 can see whether new chargers went where V1's urgency score
  said they should.

## Plan

1. **Rebuild `per_run` on all 173 samples.** Same joins and enrichment as V1
   ([DATASET_CREATION.md](DATASET_CREATION.md)). The lean selection is rerun,
   not reused, since column statistics will shift.
2. **Commit the build code.** V1's dataset was built outside this repository.
   V2's build goes in as `build_dataset.py` (or a notebook) so the dataset can
   be reproduced from `data/` alone.
3. **Compare V1 and V2.** Does the top-ranked list of carparks hold? Do
   Punggol, Sengkang and Tengah stay on top? Which carparks move, and why?
4. **A forecasting model.** With a longer series, predict next-day peak EV
   utilisation per carpark from the lagged and profile features, and use the
   forecast in place of the 14-day mean.

## How collection ended

Collection ran until 15 Oct 2026, when GitHub's artifact storage quota filled
up. The upload step ran before the commit step, so the last 8 samples were
not saved, and the workflows were then disabled. The workflows now commit
first and let a failed upload pass, so the same cause could not cost data
again if collection were ever restarted.
